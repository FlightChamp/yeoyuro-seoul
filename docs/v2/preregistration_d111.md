# D-111 사전 등록 — V4 를 광역철도 확장 켬(3-B 켬) 기본 탐색으로 바꾸기

- 상태: **사전 등록** (구현·실행 전, 2026-11-26)
- 근거: [D-110 판정 기록](candidates_d110_verdict.md) (D-110b, V4 채택). [D-110 사전 등록](preregistration_candidates.md) 7절 끝에 "채택 결과로 켬 기본 탐색 설정을 바꾸는 일은 별도 변경(새 D 번호)으로 한다. 앱 영향(성능·결과 변화)을 그때 다시 보고한다"라고 적었다. 이 문서가 그 별도 변경이다.
- 이 문서는 커밋한 뒤 고치지 않는다. 고칠 일이 생기면 새 D 번호(사후·판정·후속)를 붙인다. D-105·D-110 문서와 결과도 고치지 않는다.

## 0. 무엇을 바꾸나

| 항목 | 지금 (V0) | 바꾼 뒤 (V4) |
|---|---|---|
| 적용 범위 | — | **광역철도 확장 켬 + 3-B 켬** (`include_3b=True`) 계산기만 |
| 대표 대기 합집합 `rep_union` | 끔 | 켬 |
| GJ·GC 유사 후보 묶기 `group_gc` | 끔 | 켬 |
| 원시 후보 상한 `max_k_v3` | (안 씀) | 40 |
| k (확정 후보 수) | 10 | 10 (그대로) |

- **바꾸지 않는 것**
  - 3-B 끔(3-A만 켬) 계산기: D-110에서 평가하지 않았으므로 V0 그대로 둔다.
  - 광역철도 끔 경로(1~9호선 TDRouter)와 B1 '끔 보존' 대상은 바꾸지 않는다.
  - 평가기·검증기·정렬 규칙(실제 시간, 체감 시간)과 상태 문구는 바꾸지 않는다.
  - 라우터 클래스(`KorailTDRouter`) 자체의 기본값도 바꾸지 않는다. 앱 계산기(`ExtensionPlanner`)가 어떤 설정을 넘기는지만 바뀐다.
- 공항철도는 지금처럼 정밀 시각표 엔진을 기준으로 잰다. 집계 모델(D-108 예정)은 이 평가에 쓰지 않는다.

## 1. 순서 (커밋 단위)

1. **D-111 사전 등록** — 이 문서와 결정 기록 한 줄. 문서만 바꾼다.
2. **D-111a 구현**
   - `ExtensionPlanner(cand=...)` 옵션을 넣는다. 값은 `"v0"` 또는 `"v4"`다.
   - 모듈 기본값 `DEFAULT_CAND = "v0"`은 **바꾸지 않는다**. 앱 동작은 아직 그대로다.
   - 53에 `--cand` 옵션을 넣는다. 기본값은 `v0`이어서 D-105 재현이 그대로다.
   - 비교 도구(55)를 새로 만든다.
   - 54 평가 도구의 결함 두 가지를 고친다(6절).
   - 테스트를 넣는다.
3. **정식 실행**
   - `53 --cand v4 --tag d111` 다음에 `55`를 실행한다. 55가 G0 재현 검사와 결과 변화 비교를 함께 한다.
   - 연습(`--dry`) 결과는 보고하지 않고 판정에도 쓰지 않는다.
4. **결과 커밋** — 보고서만 커밋한다.
5. **D-111b 판정**
   - 3절 기준을 모두 통과하면 같은 패치에서 `DEFAULT_CAND = "v4"`로 바꾼다. 이때 앱 확인 스크립트(49·51)도 다시 통과해야 한다.
   - 하나라도 통과하지 못하면 기본값은 V0으로 남기고, 판정 기록만 남긴다.
   - D-111 안에서 기준을 맞추려고 설정을 다시 조정하지 않는다. 조정이 필요하면 새 D 번호로 한다.

## 2. 측정

### 2-1. 표본과 시각 (D-105 6절과 같음)
- K3B 312쌍: 3-B 역이 한쪽 이상인 무작위 300쌍(시드 42) + 지정 12쌍.
- 시각은 다섯 개다.
  - 평일 08:00·18:00·23:30 (2026-10-14)
  - 토 14:00 (2026-10-17)
  - 일 14:00 (2026-10-18)
- 비교 기준은 **재계산 b**(`reports/v2/korail_3b_eval_b.{md,json}`, 원자료 `data/marts/v2/korail_3b_eval_b/`)다. D-105e에서 통과로 판정한 V0 결과다.
  - b와 비교해도 되는지 먼저 확인한다(3절 G0). 55가 지정 12쌍 × 5시각 = 60질의를 D-111a 코드에서 `cand="v0"`으로 다시 계산해 b 원자료와 맞춘다. 다르면 비교하지 않고 그 사실부터 보고한다.

### 2-2. 53 재실행 (`--cand v4 --tag d111`)
- B1~B13을 D-105 6절 정의 그대로 다시 잰다.
- 실행 중에는 앱 모듈의 기본값도 같은 설정(v4)으로 바꿔 둔다. 그래야 앱 화면 사례(B1_app·B13_app)도 V4로 잰다.
- 민감도 변형(b·u·m·x·noGC·nodir·k20·maxonly)은 V4 설정 위에서 잰다. 이 변형들은 보고용이고 판정에 쓰지 않는다.
- 산출 위치: `reports/v2/korail_3b_eval_d111.{md,json}`, 원자료 `data/marts/v2/korail_3b_eval_d111/`. 이 원자료는 git에서 무시한다.
- 첫 보고서와 b 보고서는 덮어쓰지 않는다.

### 2-3. 결과 변화 비교 (새 도구 55)
- 입력은 b와 d111의 기본 실행 원자료다.
- 같은 질의(날짜, 시각, 출발, 도착)끼리 짝지어 아래를 보고한다.
  - 확정 추천 경로가 바뀐 건수와 비율. 시각별·묶음별(GJ·SB·AR·GC·3-B 없음)로도 나눈다.
  - 바뀐 건의 실제 시간 차이와 체감 시간 차이 분포: 최소, 중앙값, 최대, 줄어든 건수, 늘어난 건수.
  - 상태 변화 목록: 확정, 참고, 결과 없음 사이의 이동.
  - 후보 카드 수 변화.
  - plan 1회 시간: b와 d111 각각의 p50·p95·최대, 그리고 질의별 증가량 분포.
  - 메모리: psutil이 있으면 작업자 최대 RSS를 적는다. 없으면 '미측정'으로 적는다.
- 사례 목록에는 지정 12쌍 전부와 실제 시간이 가장 많이 줄어든 10건을 넣는다.

## 3. 통과 기준 (기본값을 V4 로 바꾸는 조건)

| 번호 | 기준 | 값 |
|---|---|---|
| G0 | D-111a 코드의 `cand="v0"` 재현 (지정 12쌍 × 5시각 = 60질의) | 확정 추천 경로와 정렬 키가 b와 60/60 같음. 다르면 판정을 멈추고 원인부터 보고 |
| G1 | D-105 6절 + D-105d 필수 기준 (d111 실행) | B1 불일치 0·14/14, B2 같음, B3 0, B7 보류 없음, B10 0, B11 p95 ≤ 2.6초, B13 0, 계산 오류 0, 빈칸 정차 0 |
| G2 | 확정 추천이 나빠진 질의 | **0건**. 정렬 키 (실제 시간 반올림 6자리, 체감 시간) 기준으로 d111이 b보다 뒤인 건 |
| G3 | 확정 추천이 사라진 질의 (b는 확정, d111은 확정 없음) | 0건 |
| G4 | 시간 초과·예외 | 0건 |
| G5 | pytest와 앱 확인 스크립트 49·51 | 판정 패치에서 기본값을 바꾼 상태로 모두 통과 |

- G2·G3의 이유: V4 후보는 V0 후보를 포함하고(D-110 8-A 검사), 정렬 규칙은 그대로다. 그래서 0이 기대값이다. 1건이라도 나오면 그 질의를 조사해 보고하고, 이번 D-111에서는 기본값을 바꾸지 않는다.
- 결과 변화율(2-3)에는 기준을 두지 않는다. 보고만 한다.
- 출시 목표인 p95 2.0초는 이번 판정 기준이 아니다. 따로 남은 일이다.
- 연습 결과, 그리고 한 번 실행한 뒤 고쳐서 다시 실행한 결과는 이 기준에 쓰지 않는다. 다시 실행할 일이 생기면 새 꼬리표(`d111b` 등)와 새 D 번호를 쓰고, 첫 d111 보고서는 그대로 둔다.

- 상태 문구, 카드 구성, 노선도 그림은 바꾸지 않는다. 확정 추천과 후보 순서만 바뀔 수 있다.
- 사례 화면(B13_app 등)에서 공항철도 구간이 확정 추천이 된 경우가 0건이어야 한다(G1의 B13).

## 5. 한계 (미리 적어 둠)

- D-110 감사의 남은 문제는 V4로도 남는다. k=40 감사에서 기준 경로보다 나은 경로가 11/420건 나왔다(회기→한성백제 등). D-111은 이 문제를 고치지 않는다.
- 표본이 K3B 312쌍 × 5시각이므로 3-B 역이 끼지 않은 광역 질의의 변화는 이 표본으로 알 수 없다. B4(3-A 표본)는 3-B 끔 ↔ 켬 비교라서 V4의 영향은 켬 쪽에만 들어간다.
- 시간 측정은 사용자 PC의 작업자 수와 기기 상태에 따라 달라진다. b와 d111을 같은 PC에서 같은 작업자 수로 실행하지 않았다면 그 차이를 함께 적는다.
