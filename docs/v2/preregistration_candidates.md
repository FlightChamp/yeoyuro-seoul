- 고정일: 2026-11-25. **이 문서와 D-110 은 D-110 구현·평가 결과보다 먼저 커밋·push 한다.** 결과를 본 뒤 바꾸는 항목은 새 D 번호(사후)로 따로 기록한다.
- 기준: v2-next `5a01eb9` (D-105e — 3B-4 공식 통과). 3B-4 첫 결과 `4d8c0f9`(기준 미달) · D-105d · 재계산 b `32f2ce0` 은 그대로 둔다.
- 이 문서는 **필수 기준 통과(D-105e)와 별도로 추천 품질**을 다룬다. 3B-4 판정·결과를 바꾸지 않는다.
- 표기: 【사실】 = 저장소 코드·보고서에서 확인(파일·함수 이름), 【제안·고정】 = 이 문서로 정하는 것, 【미확인】 = 구현 단계에서 확인.

## 0. 문제와 원인 【사실】

- 재계산 b(32f2ce0) 보고 항목:
  - B4 — 3-A 확정 추천 경로가 3-B 를 켠 뒤 후보 목록에 아예 없는 건(후보 밀림) 98건, 그중 기대 소요가 늘어난 건 14
  - B8 — 경춘선을 넣으면 더 나쁜 3쌍 6건: 홍대입구→망우 2026-10-14 08:00·18:00, 10-17·10-18 14:00 / 청담→회기 10-14 23:30 / 월계→도곡 10-14 23:30

- 원인: 후보 탐색(Yen)의 가중치는 주행·정차·보행만 쓰고 **대기는 넣지 않는다** (`KorailTDRouter._time_yen`, D-095 E7). 최종 평가는 대기 포함 기대 소요다. 그래서 주행이 짧고 갈아타기가 많은 경로가 후보 자리를 먼저 차지한다.
  - 예: 홍대입구→망우 08:00 — 경의중앙 직통(탐색 가중치 35.0, 기대 소요 42.5분)이 k=10·20 후보에 없고 k=40 에서 나온다. 2호선 경유 경로는 가중치 30.3 으로 앞선다 (첫 결과 샌드박스 조사).
  - 경춘선 승강장 노드(`GC_상봉`·`GC_망우`)가 거의 같은 후보를 늘려 자리 경쟁을 키운다.

## 1. 지금 코드 (V0) 【사실】

| 단계 | 코드 | 동작 |
|---|---|---|
| 후보 수 | `KORAIL_DEFAULT_K = 10` (D-099 D1), `max_k = 20` | 켬 계산기 기본 k=10 |
| A2 | `_yen_split` | 소요시간 Yen 을 K=k 로 시작해, 구조 검사(`_clean`·`_structurally_possible`)를 통과한 후보가 k 개 미만이고 Yen 이 K 개를 다 냈으면 K 를 2배로(최대 20) |
| 최솟값 그래프 | `_time_yen_min` (D-105 4-2 D1) | 김포공항 방향별 환승을 최솟값으로 바꾼 그래프의 Yen k 개를 더함 |
| A1 | `_yen_split` | 원래 1~9호선 그래프의 소요시간 Yen k 개 + 혼잡 기반(cost) Yen k 개를 더함 |
| 시간대 | `TDRouter.candidates` (multi_bin) | 출발 30분 구간부터 도착 구간까지 구간마다 `raw_paths` 를 다시 부르고 새 경로를 합침 |
| 정리 | `_clean` | 출발·도착 같은 역 노드 자르기, 재방문·구로 규칙, D-105d 한 역 노선 셋 이어 갈아타기 제외, 중복 경로 제거 |
| 평가 | `TDRouter.evaluate_od` | **모든 후보를 평가**(R3 운행 없음은 제외)해 기대 소요(`actual_time_min`) → 체감 순 정렬. 합친 뒤 k 개로 다시 자르지 않음 |
| 확정 추천 | `ExtensionPlanner.plan` | 정렬 순서대로 열차 연결 검증(`verify_connection`) → 첫 '연결 확인' 이고 공항철도가 아닌 후보. 공항철도는 '참고 경로' |
| 대표 대기 | `rep_wait`·`rep_E`·`_add_rep_wait` (D-099 D2, 민감도 전용) | 코레일 노드로 갈아타는 간선에만 대표 E 를 더한 복사본으로 Yen 을 돌린다 (**대체**, 합집합 아님) |

**코드 대조에서 나온 차이 (지시와 다른 점)**

- **`rep_E` 는 3-B 노드에서 0 을 낸다.** 열차 조회 묶음이 `"1"` 로 고정돼 있어 GJ·GC·SB·AR 열차를 찾지 못한다. 샌드박스 확인: `rep_E("GJ_왕십리")`·`SB_왕십리`·`AR_공덕`·`GC_상봉` = 0.0, `1_석계` = 2.625.
- 1~9호선 노드로 갈아타는 간선에는 대표 대기를 더하지 않는다. 그래서 D-099 `rep_wait` 를 그대로 쓰면 V2 는 3-B 에서 거의 효과가 없다.
- 따라서 V2 는 `rep_E` 를 **고쳐 쓰는 방식**으로 정한다. 새 함수를 중복으로 만들지 않고, `rep_E` 에 노드 묶음을 따르는 열차 조회를 더한다 (2-3). 3-A 노드의 값은 지금과 같아야 한다(회귀 테스트).
- A2 는 이미 K 를 최대 20 까지 늘린다. 그래서 V0 도 원시 후보를 20 개까지 볼 수 있다. V1 (k=20) 은 처음부터 20 이고 더 늘리지 않는다 (`max_k = 20` 그대로).

### 2-1. V0 재현

V0 은 재계산 b 의 기본 실행과 같아야 한다.

- 사용자 PC 에 `data/marts/v2/korail_3b_eval_b/base.parquet`·`B4_3b.parquet` 가 있으면 (시각, OD) 마다 확정 추천 경로·기대 소요·상태가 같은지 본다.
- 없으면 korail_3b_eval_b.json 의 상태 분포·확정 추천 노선 분포·후보 수와 같은지 본다.
- 다르면 판정 전에 원인부터 찾는다 (정식 평가 무효).

### 2-2. V1

- 같은 그래프·가중치·정렬에서 k 만 20 이다.
- 검사: 질의마다 V0 후보 ⊆ V1 후보. 어긋나는 질의는 수와 사례를 보고한다. Yen 동률 순서 차이일 수 있어 자동 탈락은 아니지만, 5-3 품질 보존 검사는 똑같이 적용한다.

### 2-3. V2 — 대표 대기 (D-099 `rep_wait` 를 고쳐 다시 씀)

- **대표 대기를 더하는 곳:** 탐색 가중치에서 **환승 간선**(`kind == "transfer"`)에만 더한다.
  - 출발 접근 간선(`origin_access`)에는 더하지 않는다 → 첫 승차 대기 제외(R4) 유지
  - 같은 열차 직결 통과 간선(`_is_through`)에는 더하지 않는다
  - 9호선 일반↔급행 전환 간선에는 더하지 않는다 (평가에서는 `switch_tab` 을 쓰는 별도 규칙이라 대표값을 만들지 않음, 한계로 기록)
- **대표 대기 값 (도착 노드 기준, 출발 30분 구간 하나로 고정):**
  - 코레일·3-B 노드: 그 노드에서 다음 정차역으로 가는 열차들의 30분 구간 E(`wait_profile`)를 진행 방향별로 구해 중앙값
    - 열차 조회 묶음은 노드 접두를 따른다: `1_` → "1", `GJ_` → "GJ", 단 청량리·회기·중랑 GJ 노드는 "GJC"(경의중앙·경춘 합집합), `GC_` → "GC", `SB_` → "SB", `AR_` → "AR"
    - 3-A 노드의 값은 지금 `rep_E` 와 같아야 한다
  - 1~9호선 노드: 그 노드 노선·역의 방향별 배차÷2(평가기 `_wait` 와 같은 값, 12분 상한 포함)의 중앙값
- **중복 합산 없음:** 대표 대기는 탐색 가중치 복사본에만 들어가고 간선·평가에는 들어가지 않는다 (`_time_yen` 의 복사본 방식 그대로).
- **합집합:** V0 의 `_yen_split` 결과에 대표 대기 Yen 결과를 더하고, 합친 뒤 k 개로 자르지 않는다 (`evaluate_od` 가 전부 평가).
- **한계 (보고서에 적음):**
  - 대표 대기는 출발 구간 하나의 정적 근사다. 실제 환승 시각의 구간·목적지 필터(E2)와 다를 수 있다
  - 방향 중앙값이라 실제 진행 방향 값과 다를 수 있다
  - 최종 평가는 지금의 시간 의존 E2·열차 검증 그대로다
- **【미확인】** 고친 `rep_E` 가 3-B 노드에서 0 이 아닌 값을 내는지, 3-A 값이 그대로인지 → 구현 단계 테스트로 먼저 확인.

### 2-4. V3 — GJ·GC 유사 후보 묶기

- **탐색 묶음 키(구조 서명):** 경로를 같은 역 구간으로 나눈 (역, 노선) 순서. 노선은 노드 접두이며 **GC 를 GJ 로 바꿔 쓴다** (9L·9X 는 그대로).
  - 예: `…GJ_중랑|GJ_상봉|GJ_망우` 와 `…GJ_중랑|GC_상봉|GC_망우` 는 같은 묶음
- **쓰는 곳은 A2 루프의 '유효 후보 수 세기' 하나뿐이다.**
  - 유효 후보 = 지금과 같은 구조 검사 통과. 이 수를 경로 수가 아니라 서로 다른 묶음 키 수로 센다
  - 그 수가 k 미만이면 K 를 2배로 늘린다
- **아무 경로도 지우지 않는다.** 같은 묶음의 경로는 모두 원래 노드 그대로 후보에 남고, 평가·열차 검증은 실제 노드·운행 묶음으로 한다 (상봉·망우 승강장 차이, GJ·GC 열차 구분 보존).
- **비용 상한 (고정):** 원시 후보 K 의 최대값 **40** (`max_k_v3 = 40`). 멈추는 조건은 셋 중 하나다.
  1. 묶음 수 ≥ k
  2. K ≥ 40
  3. Yen 이 K 개보다 적게 냄 (경로 소진)

  최솟값 그래프·A1·multi_bin 은 V0 과 같다.
- **안전 판단:** 경로를 지우지 않고 더 찾기만 하므로, 구조가 비슷하다는 이유로 유효 경로가 사라지지 않는다. 남는 위험은 Yen 결과의 앞부분이 K 에 따라 달라지는 경우뿐이다 (8-A 검사).

### 2-5. V4

- V2 의 두 Yen(대표 대기 없음·있음)에 모두 V3 세기 규칙을 쓴다. 원시 후보 상한은 각 40.

### 2-6. V5 — 3-A 후보 보존

- 같은 요일·조회 날짜의 3-A 켬 계산기(`KorailTDRouter(include_korail=True, include_3b=False)`, 지금 확장 기능에서 3-B 만 끈 상태 — **1~9호선 끔 계산기가 아님**)로 같은 질의의 후보를 만든다. A1·A2·k=10·multi_bin 은 그 계산기 규칙대로다.
- 그 후보를 V0(3-B 켬) 후보에 더하고, **3-B 켬 평가기·검증기로 다시 평가**한다. 3-A 경로를 1순위로 고정하지 않는다.
- 비용: 계산기 하나 더(준비 시간·메모리), 질의마다 후보 생성 한 번 더 → 6절 성능 측정에 포함.

## 3. 평가 실행 설계 【고정】

### 3-1. 입력과 중복 제거

- 품질 표본:
  - K3B 312쌍 × 5시각 (D-105 6절: 2026-10-14 08:00·18:00·23:30, 10-17 14:00, 10-18 14:00)
  - B4 = 3-A K 412쌍 × 2026-10-14 07:30·08:00·08:30·17:30·18:00·18:30
  - 요청 합계 4,032건
- 평가 입력 키: (출발역, 도착역, 운행일 날짜, 운행일 분, 통계 요일, 시각표 요일, 3-A·3-B 켬 상태, 정책 옵션 해시, 코드 커밋, 3-B 정차표 SHA-256).
  - 키가 같은 입력은 한 번만 계산하고 두 표본 집계에 다시 쓴다
  - 요청 건수·중복 건수·고유 건수를 보고한다
- 모든 방법은 같은 고유 입력 전체를 평가한다. 결과를 본 뒤 표본을 줄이지 않는다.

### 3-2. 품질 평가의 결과 재사용 (질의 안에서만)

- 한 질의에서 V0~V5 후보를 모두 만든 뒤 경로 합집합을 **한 번씩** 평가·검증하고, 방법마다 자기 후보 부분집합으로 확정 추천을 고른다 (`ExtensionPlanner.plan` 과 같은 정렬·선택 규칙).
- 재사용 키: (실제 노드 순서 그대로 — GJ·GC 노드 구분 포함, 운행일 분, 시각표 요일, 평가기 설정 해시, 검증 색인 설정). **물리적 역 순서만 같은 다른 노드 경로는 공유하지 않는다.**
- 평가기·검증 색인은 방법과 상관없이 같다 (대표 대기는 탐색 복사본에만, V5 도 3-B 평가기). 그래서 같은 경로의 결과는 방법에 따라 달라지지 않는다.
- 교차 검증: 고정 소표본 40질의(시드 1101)에서 '방법마다 따로 `plan()`' 과 '합집합 평가 뒤 선택' 의 확정 추천·참고 경로·상태·기대 소요가 모두 같아야 한다. 하나라도 다르면 정식 평가로 넘어가지 않는다 (캐시·상태 누수·비결정성 조사).

### 3-3. 독립 성능 평가 (p95 판정용)

- 품질 평가의 재사용 결과는 쓰지 않는다. 방법마다 새 계산기를 만들어, 앱과 같은 데이터 적재·캐시 정책으로 `plan()` 을 사용자 요청 하나씩 순서대로 부른다 (작업자 1개, 다른 계산 동시 실행 없음).
- 성능 표본 (고정): 품질 고유 입력에서 시드 1102 로 **300질의** 층화 무작위 추출.

## 4. 비교 기준 — Best-known reference 【고정】

### 4-1. 전체 공통 참고 집합

- 고유 입력마다 V0~V5 후보 합집합을 같은 평가기·검증기·선택 규칙으로 평가한다. 그중 확정 추천이 될 수 있는 최선(기대 소요 최소, 같으면 체감 최소)을 참값으로 둔다.
- 한계: 실험에 들어간 방법들의 합집합이다. 모든 방법이 함께 놓친 경로는 잡지 못한다 → 4-2.

### 4-2. k=40 심층 감사 (고정 감사 표본에서만)

감사 표본 (모두 이번 V0 실행 결과로 정하는 규칙):

| 묶음 | 규칙 |

| D6 층화 무작위 | D1~D5 밖 고유 입력에서 시드 1103 으로 200질의, 3-1 층 비례 |

- 보고: 감사 표본에서 k=40 이 4-1 참값보다 나은 경로를 찾은 수와 차이, 방법별 놓침을 '감사 참값' 기준으로 다시 센 값.

- k=80 은 D2·D3·D5 에만 추가로 한다.
- 어느 경우에도 '전역 최적' 이라고 쓰지 않는다.

## 5. 품질 지표 【고정】

### 5-1. 주요 지표

- **M = 4-1 참값 대비 확정 추천 기대 소요 손실 > 0.5분인 고유 입력 수.**
- 손실 계산 규칙:
  - 방법에 확정 추천이 없고 참값에는 있으면 '확정 추천 누락' 으로 M 에 넣는다 (손실 = 무한대로 셈)
  - 둘 다 없으면 손실 0
  - 운행 종료·경로 미발견·자료 부족은 사유별로 따로 센다
- 보조 지표:
  - 손실 > 0분 건수, 손실 > 1분 건수
  - 손실 중앙값·P95·최대 (누락 제외)
  - 참값과 확정 추천 경로 일치율
  - 참값 경로가 그 방법 후보에 있는 비율
  - 추가 후보(V0 에 없던 것) 중 확정 추천이 된 비율
  - 후보 수 증가 대비 M 감소
- 표본별(K3B·B4)·시각별로도 나눠 보고한다.

### 5-2. 표적 사례

- 4-2 D1~D5 각각에서 해결된 수(참값과 같은 확정 추천)를 센다.
- 지정 사례(홍대입구→망우·청담→회기 23:30·월계→도곡 23:30·수색→강남구청)는 후보 생성·평가·검증·확정 추천 중 어디가 달라졌는지 기록한다.
- 표적 성과가 좋아도 6절 자격이나 5-3 을 어기면 채택하지 않는다.

### 5-3. V0 품질 보존 (필수 불변조건)

목적함수는 지금 확장 카드와 같다: 기대 소요 → 체감 순 정렬, 열차 연결 확인, 공항철도 제외. 혼잡 미확인 구간은 0% 로 바꾸지 않는다.

방법 M 이 고유 입력 q 에서 **V0 보다 나쁨** = 다음 중 하나:
- (a) V0 에 확정 추천이 있는데 M 에 없음
- (b) 둘 다 있고 M 의 기대 소요 > V0 의 기대 소요 + 1e-6
- (c) V0 확정 추천이 있는데 M 은 참고 경로만 있음

**나쁨 건수는 0 이어야 한다.** 같은 경로를 V0 과 M 이 다르게 평가하면 계산 결함으로 보고 판정 전에 조사한다.

## 7. 채택 규칙 (수식 고정) 【고정】

```
E   = { V1..V5 중 6절 자격을 모두 만족한 방법 }
M0  = V0 의 M (5-1)
1) M0 = 0                          → V0 유지 (개선할 놓침 없음)
2) I  = { i ∈ E : M_i < M0 };  I = ∅ → V0 유지
3) M_best = min_{i∈I} M_i
   Δ      = floor(0.10 × M0)
   C      = { i ∈ I : M_i − M_best ≤ Δ }        (V0 는 C 에 넣지 않음)
   p_min  = min_{i∈C} p95_i
   T      = { i ∈ C : p95_i − p_min ≤ 0.05초 }   (측정 변동 = 실질 동률)
4) T 에서 차례로 하나가 남을 때까지 좁힌다
   ① M_i 가장 작은 것
   ② '검증한 추가 후보 수'(V0 에 없던 후보 중 열차 검증한 수, 품질 평가 합계)가 가장 적은 것
   ③ 구현 단순성 순서 V1 < V5 < V2 < V3 < V4 (앞이 단순)
   ④ 방법 ID 순서 V1 < V2 < V3 < V4 < V5
5) 남은 하나를 채택. 1)·2) 로 끝나면 V0 유지
```

- V0 유지로 끝나면 남은 표적 사례와 탐색 한계를 보고하고, 다른 접근은 새 D 번호에서 검토한다.
- 채택 결과로 켬 기본 탐색 설정을 바꾸는 일은 **별도 변경**(새 D 번호)으로 한다. 앱 영향(성능·결과 변화)을 그때 다시 보고한다.
- 결과를 본 뒤 이 규칙·지표·표본·예산을 바꾸지 않는다.
