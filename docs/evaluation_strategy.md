## A. 데이터 품질 — 스키마 검증

### 문제 유형
원본이 바뀌었을 때(스키마 드리프트, 역명 변경, 값 범위 이탈) 조용히 잘못된 마트가 만들어지는 것을 막아야 한다.

### 왜 pandera 인가
- 사람이 읽는 리포트는 읽지 않으면 아무 일도 일어나지 않는다. 스키마 검증은 **깨지면 파이프라인이 멈추는 테스트**다.
- Great Expectations 는 기각했다. 리포트 기능이 강하지만 이 규모에서는 오버엔지니어링이고, pandera 로 충분하다.

### 결과 (`11_validate_schemas.py --strict`)

| 구분 | 결과 |
|---|---|
| 테이블 스키마 | PASS 7 / FAIL 0 |
| 교차 검증 | PASS 10 / FAIL 0 |

교차 검증은 단일 테이블 스키마로 못 잡는 것을 본다.

- split 이 스냅샷 단위로 배타적인가 (**누수 방지의 핵심**)
- 응암순환이 단방향인가 (정방향 6/6, 역방향 0)
- 미운행 행이 `congestion_rate` 결측인가 (`fillna(0)` 사고 방지)
- 환승역 마스터 35개가 그래프에 모두 존재하는가

### 이 검증이 잡으려는 실제 사고
전부 이 프로젝트에서 실제로 겪은 것이다.

1. 혼잡도 원본 스키마가 3종으로 갈라짐
2. 5호선 둔촌동·올림픽공원이 2호선으로 잘못 기재된 156행
3. 두 마트의 `station_uid` 규칙이 달라 조인 매칭률 0%
4. 첫 실행에서 `perceived_multiplier` FAIL → **스키마 쪽이 틀렸음**을 발견하고 조건부 검증으로 수정

## B. 이벤트 효과 — 인과 효과 추정

### 문제 유형
"이벤트가 있었다"가 아니라 **"이벤트가 얼마나 튀게 했나"**를 추정하는 문제다. 공식 캘린더를 그대로 피처로 넣으면 효과 없는 이벤트가 노이즈가 된다.

### 왜 DiD 인가
`spike_ratio` 는 대조군 없는 전후 비교다. 그날 서울 전체 통행량이 많았다면 배율이 부풀려진다.

```
spike_ratio = 여의나루 당일 / 여의나루 평소          (전후 비교)
DiD         = (처치군 변화) − (대조군 변화)          (순효과)
```

**대조군 선정 규칙**
1. 어떤 이벤트의 anchor/impact 역도 아닌 역
2. **spillover 제외**: 같은 노선 3정거장 이내는 제외 (인파가 번지면 대조군 오염)
3. 평소 이용 규모(log 일평균) 최근접 5개
4. **평행추세 검증**: 이벤트 직전 4주 추세 차이가 0.15 이내

### 결과

| 유형 | 전후비교 | **DiD 순효과** | 절대증가(중앙값) |
|---|---|---|---|
| fireworks | 3.674 | **3.403** | 81,117명 |
| cherry_blossom | 2.476 | **2.370** | 45,623명 |
| essay | 1.301 | **1.267** | 9,411명 |
| halloween_proxy | 1.200 | **1.166** | 14,848명 |
| transfer_exam | 1.145 | **1.114** | 2,970명 |
| new_year_bell | 1.002 | **1.010** | 1,180명 |

**숫자가 작아진 것이 정확해진 것이다.** 전후 비교가 도시 전체 트렌드를 흡수해 과대추정하고 있었다.

### absolute_lift 를 함께 쓰는 이유
비율만 보면 왜곡된다. 평소 10명이 100명이면 10배지만 증가는 90명이고, 3,000명이 6,000명이면 2배지만 증가는 3,000명이다. 지하철 혼잡 관점에서는 후자가 더 중요할 수 있다.

실제로 편입시험은 배율 1.114 로 약하지만 절대 증가 2,970명, 할로윈은 배율이 비슷한데 14,848명이다.

### 평행추세 검증이 잡은 것
- 충족 159행 / **위반 28행**
- **할로윈 2022(이태원)** 위반 → 이미 `exclude_from_training` 으로 뺀 이벤트인데 **독립적인 두 번째 근거**가 생겼다
- **봄꽃축제 2023, 불꽃축제 2022~2024** 위반 → 축제 전주부터 이미 붐비기 시작. `official_period` 와 `actual_impact_window` 분리 설계가 지지된다

### 한계
회귀 기반 DiD 가 아니라 비율 차분(DiD-lite)이라 표준오차를 내지 않는다. 대조군은 규모 유사성만으로 매칭했고 상권 성격은 통제하지 않았다.

## C. 혼잡도 예측 — 회귀 + 불균형 분류

### 사전 등록한 통과 조건
학습 **전에** 정했고, 결과를 보고 바꾸지 않았다.

> LightGBM 이 `역 × 방향 × 요일유형 × 시간대 평균` baseline 을 valid 에서 이기지 못하면, 모델을 폐기하고 baseline 을 서비스에 사용한다.

### C-1. Baseline ladder — 어느 정보가 얼마나 기여하나

| 수준 | MAE | R² | PR-AUC | 미관측 역 coverage |
|---|---|---|---|---|
| L0 전체평균 | 15.342 | 0.000 | 0.056 | 1.00 |
| L1 노선×방향×요일×시간대 | 11.115 | 0.400 | 0.134 | 1.00 |
| **L2 역×방향×요일×시간대** | **2.364** | **0.947** | **0.857** | **0.00** |
| L3 L2+최근스냅샷 | 2.763 | 0.928 | 0.847 | 0.00 |

- L1→L2 에서 MAE 가 11.1→2.4 로 급락한다. 혼잡도를 결정하는 것은 압도적으로 "어느 역인가"다.
- L3 가 L2 보다 나쁘다. 최신 스냅샷 하나보다 6개 평균이 안정적이다. **recency 가 도움이 안 된다**는 발견이다.

### C-2. Skill Score

MASE 는 시계열 naive forecast 를 분모로 쓰는 지표라 격자 회귀인 이 문제에 정의가 맞지 않는다. 정의가 정확한 Skill Score 를 쓴다.

```
Skill Score = 1 − MAE_model / MAE_reference     (양수면 개선)

Regime A  LGBM(전체) vs L2 baseline        : −0.464
Regime B  LGBM(식별자 제외) vs L1 baseline : −0.012
```

Regime B 의 −0.012 는 사실상 동률이다. "모델이 졌다"가 아니라 **"노선 평균과 구별이 안 된다"**가 정확한 서술이다.

### C-3. 불균형 분류 지표

고혼잡 라벨은 5.66% 다. Accuracy 는 무의미하고 단일 임계 F1 도 임계에 의존한다.

| 수준 | PR-AUC | Recall@P≥0.5 | base rate |
|---|---|---|---|
| L0 | 0.056 | 0.000 | 0.057 |
| L1 | 0.134 | 0.000 | 0.057 |
| **L2** | **0.857** | **0.892** | 0.057 |

**라벨 정의를 바꾼 이유**: 기획서 v1 의 130%/150% 절대 임계는 각각 전체의 0.087%, **38셀(0.005%)** 이라 평가지표가 불안정해진다. 역×방향별 train p95 분위수 라벨(5.25%)로 전환했다.

### C-4. Ablation study

| 피처군 | MAE | R² | PR-AUC |
|---|---|---|---|
| A. 시간만 | 11.235 | 0.391 | 0.136 |
| B. +역속성 | 10.518 | 0.450 | 0.146 |
| **C. +승하차flow** | **6.986** | **0.734** | **0.245** |
| D. +역식별자 | 3.460 | 0.916 | 0.718 |

**B→C 가 이 프로젝트의 핵심 근거다.** 승하차 흐름을 넣자 R² 가 0.45→0.73 으로 뛴다. 48개월 승하차 데이터를 쓰는 이유가 수치로 증명된다.

C→D 도 정직하게 본다. 역 식별자를 넣으면 R² 가 0.92 로 또 뛴다. **모델이 역을 외우고 있다**는 뜻이고, baseline 이 이기는 이유이기도 하다.

### C-5. SHAP — Model-2 에만 적용

08 판정에서 채택된 것은 baseline 이고, 모델은 **미관측 역 보간용 Model-2** 다. 폐기한 Model-1 을 설명하는 것은 앞뒤가 맞지 않는다.

| 피처 | 기여 |
|---|---|
| day_type | 13.4% |
| time_bin_index | 12.4% |
| log_flow_total | 10.6% |
| line_id | 9.5% |
| boarding_cnt | 9.4% |
| flow_total | 8.5% |
| station_flow_total | 5.9% |

승하차 계열 4종이 합쳐 **34.4%**. "역이 어디인지 모르는 상태에서 무엇으로 혼잡도를 설명하는가"에 대한 답이다.

### C-6. Error analysis — 반드시 밝혀야 할 것

| 혼잡 구간 | 건수 | MAE |
|---|---|---|
| ~30% | 95,464 | 1.474 |
| 60-80% | 6,920 | 5.951 |
| 100-130% | 825 | 9.057 |
| **130%+** | 136 | **9.227** |

**정작 중요한 고혼잡 영역에서 6배 부정확하다.** "MAE 2.36" 이라는 전체 평균이 저혼잡 구간에 희석된 결과라는 것을 밝히지 않으면 정확히 이 지점을 공격당한다.

노선별로는 8호선(MAE 3.600, p95 오차 13.9)과 2호선(2.943)이 나쁘고 3호선(1.615), 7호선(1.760)이 좋다.

### C-7. 알려진 편향 (리포트에 명시)
`label_high` 는 역×방향별 train p95 로 정의된다. station holdout 의 역은 train 에 없어 전역 p95 로 대체된다. 즉 **미관측 역의 라벨 기준이 다른 역과 다르며**, Regime B 의 분류 지표는 이 편향 위에서 계산된 값이다.

### 결론
1. 사전 등록한 조건대로 **baseline(L2)을 서비스에 사용한다.**
2. 다만 baseline 은 미관측 역에서 **coverage 0** 이다. 신설역이 생기면 무력하므로 Model-2 를 보간용으로 유지한다.
3. 모델의 가치는 예측 정확도가 아니라 **설명과 보간**에 있다.

## D. 경로 추천 — 다목적 최적화

### 문제 유형
경로 추천에는 **정답 경로가 없다.** Accuracy 계열도, NDCG 같은 랭킹 지표도 쓸 수 없다(사용자 피드백 라벨이 없다). 다목적 최적화의 표준 도구를 쓴다.

### D-1. 3축 Pareto optimality

```
obj1 actual_time_min       (작을수록 좋음)
obj2 max_congestion        (작을수록 좋음)
obj3 transfer_penalty_min  (작을수록 좋음)
```

**왜 3축인가.** 2축(시간·혼잡)만 쓰면 아래가 탈락한다.

```
A: 30분 / 120% / 환승 2회
B: 31분 / 122% / 환승 0회     ← 2축에서는 dominated
```

B 는 시간도 혼잡도 A 보다 나쁘지만, 환승 없는 직통은 실제 이용자에게 좋은 대안일 수 있다. 환승 부담을 별도 축으로 두어 후보를 보존한다.

`transfer_count` 가 아니라 `transfer_penalty_min` 을 축으로 쓴다. 환승 1회라도 긴 환승이면 부담이 크고, 2회라도 짧으면 낮기 때문이다.

**Pareto 는 후보 보존 장치이지 최종 순위가 아니다.** 최종 순위는 `perceived_time_min` 기반 모드별 scoring 으로 정한다.

### D-2. Stretch Factor

```
Stretch Factor = candidate_time / fastest_time
```
OD 간 비교가 가능하도록 정규화한다. 대표 시각화의 x축이다.

### D-3. Directed-edge Jaccard

경로 다양성은 **노드가 아니라 방향 있는 엣지** 기준으로 잰다.

```
edge = (from_node, to_node, line_id, direction)
```

순환선(2호선 내선/외선), 왕복 지선, 단방향 순환(6호선 응암)이 있어 같은 역을 지나도 실제 구간이 다를 수 있다. 임계 0.65 초과는 near-duplicate 로 표시한다.

**발견한 버그**: near-duplicate 제거를 route_score 순으로만 하면, 혼잡이 오히려 늘어나는 dominated 경로가 먼저 자리를 잡고 **Pareto 최적해를 몰아낼 수 있다**(방화→마천 18:00 에서 −27.8%p 해가 잘렸다). Pareto optimal 을 먼저 처리하도록 순서를 바꿨다.

### D-4. 결과

| 조건 | 경로 대안 | Pareto front 평균 |
|---|---|---|
| 평일 08:30 | **3/13** | 2.08 |
| 평일 18:00 | **2/13** | 2.15 |
| 불꽃축제일 18:00(토) | **2/13** (calm) · 3/13 (그 외 모드) | 2.46 |

> 이 표는 `10_evaluate_routes.py` 의 비용 계산을 `RouteScorer.evaluate()` 로
> 통합한 뒤의 값이다. 통합 전에는 중간역 정차시간과 강동 직결 분기 통과가
> 리포트에 반영되지 않았다. 경위는
> [`dwell_time_adjustment_report.md`](dwell_time_adjustment_report.md) §6 참고.

**핵심 발견 두 가지.**

1. **최단경로를 대체할 수 있는 쾌적 대안은 일부 OD 에서만 나타난다.** 오전 3/13, 저녁 2/13 이다. 개수 차이는 크지 않지만 **구성이 다르다.** 08:30 과 18:00 에서 대안이 잡히는 OD 가 서로 겹치지 않는다.
2. **이벤트는 대안의 개수가 아니라 구성을 바꾼다.** 불꽃축제일 18:00 은 선호 모드에 따라 추천 경로가 갈린다(calm 2/13, 그 외 3/13). 평시에는 모드가 달라도 채택 결과가 같았다. 국소적 혼잡이 특정 축의 비용만 밀어올리기 때문이다.

18:00 의 Pareto front 가 더 크지만(2.15 > 2.08) 채택되는 대안은 더 적다. **수학적 최적성과 서비스 가치는 다르다**는 것을 보여준다. 무엇이 걸러내는지는 아래 임계 민감도에서 조건 단위로 확인할 수 있다.

### D-5. 대안 없음 정책

모든 OD 에서 억지로 대안을 만들지 않는다.

```
채택 조건: time_loss ≤ 15분 AND 최대혼잡 감소 ≥ 15%p
           AND 체감시간 ≤ 최속 + 5분 AND not near_duplicate
미달 시:   recommendation_policy = "no_meaningful_alternative"
```

**임계 민감도 분석**으로 어느 조건이 병목인지 밝힌다. 각 칸은 "이 조건만 풀면 대안이 생기는 요청 수" 다(요청 52건 기준).

| 조건 | 08:30 | 18:00 | 불꽃축제 18:00 |
|---|---|---|---|
| `cong_drop` 최대혼잡 −15%p 이상 | 25 | **28** | **28** |
| `perceived` 체감시간 최속+5분 이내 | 8 | 0 | 0 |
| `time_loss` 소요시간 +15분 이내 | 0 | 0 | 0 |
| `near_duplicate` 제거(Jaccard 0.65 초과) | 24 | 20 | 25 |

**저녁은 혼잡 감소폭 단일 병목이다.** 오전에는 체감시간 조건도 8건을 걸러내지만
저녁에는 0건이다. 즉 저녁에 대안이 적은 이유는 "우회 경로가 없어서" 가 아니라
**우회해도 최대 혼잡도가 15%p 이상 내려가지 않기 때문**이다. 도심 전체가 고르게
붐빈다는 해석이 개수 비교가 아니라 조건 단위로 뒷받침된다.

시간 손실(15분)은 세 시나리오 모두 병목이 아니다(not binding). 후보 경로들이
애초에 크게 돌아가지 않는다는 뜻이다.

`near_duplicate` 가 20~25건인 것도 의미가 있다. 후보의 상당수가 사실상 같은
경로이며, directed-edge Jaccard 로 거르지 않으면 "대안" 이 과대 집계된다.

임계값(15분/15%p/5분)은 근거 있는 상수가 아니라 **튜닝 대상 초기값**임을 명시한다.

`pareto_front_size = 1` 인 OD 는 trade-off 자체가 존재하지 않는다. 임의 임계값이 아니라 **수학적으로** 대안이 없음을 보인다.

### D-6. 그래프 모델링 결함과 회귀 테스트

다목적 최적화 이전에, **그래프가 현실을 잘못 표현하면 어떤 지표도 의미가 없다.**
공개 데이터를 그대로 엣지로 만들었을 때 실제로 존재하지 않는 경로가 나왔다.

| 결함 | 증상 | 대응 |
|---|---|---|
| 분기역 단일 노드 | 지선 승객이 갈아타지 않고 통과 | 성수·신도림·강동 노드 분리 |
| 6호선 응암순환 단일 노드 | `구산 → 응암 → 역촌` 환승 0회 | 순환 종료 노드 분리 + 재승차 환승 엣지 |
| U턴 무비용 | `구산 → 응암 → 새절 → 응암 → 역촌` 로 재승차 우회 | **역 재방문 금지** 제약 |
| 환승 호차/문 방향 무시 | 잠실 8→2 에서 반대 방면 위치 안내 | 경로 앞뒤 역으로 방면 매칭 |
| **직결 분기를 셔틀 지선과 동일 취급** | 광나루→오금이 강동 환승 1회로 안내 | 경로 앞뒤 노드로 통과 판정. 하남↔마천만 환승 |

**마지막 항목은 첫 번째 대응이 과했던 경우다.** 5호선 강동을 성수·신도림과
같은 방식으로 나눈 것이 원인이었다.

근거는 서울교통공사 `열차운행현황` 의 구간 표기다.

```
5호선 : 방화~하남검단산/마천          영업거리 59.8      시격 2.5/6.5   운행횟수 428
2호선 : 성수~성수[성수지선/신정지선]     영업거리 48.8[5.4/6.0]           운행횟수 528[226/220]
```

2호선 지선은 대괄호로 분리돼 **별도 시격·별도 운행횟수**를 갖는 셔틀이다.
반면 5호선은 마천지선을 포함해 **단일 계통**으로 집계된다. 방화에서 출발한
열차가 강동에서 갈라져 하남검단산행과 마천행으로 직결 운행한다는 뜻이다.

강동에서 일어나는 이동은 세 가지인데, 분기 엣지 하나로는 둘을 구분할 수 없다.

| 이동 | 실제 | v1 모델 |
|---|---|---|
| 천호(본선) ↔ 길동(하남) | 직통 | 직통 |
| 천호(본선) ↔ 둔촌동(마천) | **직통** | **환승 1회** |
| 길동(하남) ↔ 둔촌동(마천) | 환승 필요 | 환승 1회 |

같은 엣지라도 천호에서 왔으면 통과이고 길동에서 왔으면 환승이다.
엣지 가중치로는 표현되지 않으므로 `evaluate()` 에서 **경로의 앞뒤 노드**를 보고
판정한다. 통과일 때는 승차 구간을 끊지 않으므로 분기역이 중간 정차역으로 계산된다.

회귀 테스트는 **미적용과 과잉적용을 각각 다른 테스트가 검출**하도록 짰다.
통과 예외를 없애면 `trunk_to_macheon_is_not_a_transfer` 계열이 실패하고,
무조건 통과로 바꾸면 `branch_to_branch_still_transfers` 계열이 실패한다.
한쪽만 검증하는 테스트였다면 과잉 수정을 놓쳤을 것이다.

**근본 해결은 계통 분리다.** 5호선을 두 계통(방화~하남검단산 / 방화~마천)으로
복제하고 공통구간 38개 역이 각각 노드를 갖게 하면, 광나루에서 마천행을 기다릴지
강동까지 가서 갈아탈지를 알고리즘이 비교하게 된다. 현재는 예외 처리이며
계통 분리는 v2 과제로 남긴다.

**U턴은 배차가 긴 낮 시간대에만 나타났다.** 08:30 으로만 검증했을 때는 통과했고,
13:30 에서 재승차 대기시간이 커지자 U턴이 더 싸게 나왔다.
그래서 회귀 테스트를 **5개 시간대**(08:30 / 11:30 / 13:30 / 19:00 / 22:00)로 돌린다.

테스트가 실제로 결함을 잡는지도 확인했다. 재방문 필터를 일시 제거하자
11:30 / 13:30 / 22:00 에서만 5건이 실패했다. 통과만 확인한 테스트는 아무것도 보장하지 않는다.

현재 `tests/` 는 116개다(경로 41 · 정차 18 · 방면 27 · 표시 정합 13 · 직결 분기 17).

### D-7. 환승 대기시간 (v1 MVP)

30분 단위 평균 배차간격으로 **환승 후 다음 노선 승차 전 대기시간**을 추정해
소요시간·체감시간에 더한다.

```
headway_freq_min  = 30 / n_departures
expected_wait_min = headway_freq_min / 2      (균등 도착 가정, 상한 12분)
```

**점수 계산 전에 더한다.** 표시만 하고 순위에 넣지 않으면
"환승 1회지만 배차가 긴 노선"과 "환승 2회지만 자주 오는 노선"을 비교할 수 없다.

**최초 승차 전 대기는 반영하지 않는다.** 사용자가 승강장에 도착하는 시점을 알 수 없어
출발 시각 입력의 의미가 흐려진다. 특정 시각의 실제 다음 열차를 찾는 것은 v2 과제다.

### D-8. 한계
Pareto front 가 계산되는 후보 집합은 **Yen's K-shortest 가 만든 것에 한정**된다. 진짜 Pareto front 가 아니라 "K개 후보 안에서의 front" 다. 다목적 최단경로(MOSP) 알고리즘을 쓰면 해결되지만 이 규모에서는 과하다.

## E. 착석 가능성 — 검증 불가

좌석 점유 데이터가 없다. `seat_chance_score` 는 혼잡도 급감 구간을 기반으로 한 **proxy 점수**이고, 정답이 없으므로 **평가 자체가 불가능하다.**

- "착석 확률"이라고 표현하지 않는다.
- 별도 평가 지표를 만들지 않는다. 만들면 검증한 척이 된다.
- 경로 순위에만 보조적으로 반영하고, 단독 기능으로 내세우지 않는다.

같은 이유로 다음도 평가 대상에서 제외한다.

| 항목 | 사유 |
|---|---|
| 실시간 혼잡도 | 실시간 API 없음 |
| 객차별 혼잡도 | 객차 단위 재차 데이터 없음 |
| 이벤트 당일 실제 혼잡도 | 혼잡도가 분기 평균 패턴 |
| 사용자 만족도 | 사용자·피드백 없음 |

## F. 도입하지 않은 것과 그 이유

면접에서 "왜 안 썼나"에 답할 수 있어야 한다.

| 후보 | 판단 | 이유 |
|---|---|---|
| **LSTM / Transformer** | 기각 | 혼잡도 스냅샷이 **11개**다. 격자당 관측치 11개에 딥러닝을 쓰면 과적합만 남는다 |
| **GNN** | 기각 | 그래프 구조가 있다고 바로 쓰는 게 아니다. 학습 목적과 라벨이 명확하지 않다 |
| **NDCG / MAP** | 기각 | 랭킹 지표는 정답 선호도 라벨이 필요하다. 사용자 피드백이 없다 |
| **MASE** | 기각(자기수정) | 시계열 naive forecast 를 분모로 쓰는 지표라 격자 회귀에 정의가 맞지 않는다. Skill Score 로 대체 |
| **정밀 시각표 next departure** | v2 | 특정 시각의 실제 다음 열차 계산. v1 은 30분 bin 평균으로 대체 |
| **Hypervolume** | 보류 | 기준점(reference point)을 임의로 정해야 하고 그 선택이 값을 좌우한다. 목적 2~3개·후보 5~9개 규모에서는 과하다 |
| **Great Expectations** | 기각 | pandera 로 충분. 두 개 쓰면 오버엔지니어링 |
| **MLflow** | 기각 | 학습이 사실상 1회다. 하이퍼파라미터 탐색을 하지 않는데 실험 추적 도구를 쓰면 도구를 위한 도구가 된다 |
| **API latency p50/p95** | 기각 | 280노드 그래프의 응답속도는 데이터 역량과 무관하다 |
| **A/B 테스트** | 기각 | 사용자가 없다 |

## H. 면접 요약 문장

> 각 단계의 문제 유형을 먼저 식별하고 표준 평가 체계를 붙였습니다.
> 이벤트 효과는 인과 추정 문제라 대조군을 둔 이중차분으로 순효과를 분리했고, 평행추세 위반 28건을 걸러냈습니다.
> 혼잡도 예측은 불균형 분류라 Accuracy 대신 PR-AUC 를 썼고, 학습 전에 정한 조건대로 LightGBM 이 baseline 을 이기지 못하자 baseline 을 채택했습니다.
> 경로 추천은 정답이 없는 다목적 최적화라 3축 Pareto optimality 로 후보의 열등 여부를 판단하고 Stretch Factor 로 시간·혼잡 trade-off 를 정규화했습니다.
> 착석 가능성은 정답 데이터가 없어 평가 자체를 하지 않았고, 그 사실을 문서에 남겼습니다.
