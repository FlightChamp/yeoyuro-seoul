# 중간역 정차시간(dwell time) 보정 리포트

> 작업 범위: 경로 소요시간에 중간역 정차시간을 반영한다.
> 원본 시각표 정밀 파싱, next departure, 혼잡도 재학습, 지도 UI, 9호선 확장은 범위 밖이다.

---

## 1. 문제

여유로 서울 의 경로 소요시간이 일반 길찾기 서비스보다 짧게 나왔다.
그래프의 승차 엣지 가중치가 순수 주행시간이고 정차시간이 빠져 있을 가능성을 확인했다.

## 2. 확인 — 원본에 정차시간이 포함되어 있는가

**결론: 포함되어 있지 않다 (Case B).**

`data/raw/route_distance_time/서울교통공사_역간거리_및_소요시간_240810.csv` 의 `소요시간`
컬럼(mm:ss)을 `06_build_route_graph.py` 가 그대로 `travel_time_min` 으로 쓴다.
06 은 어떤 보정도 하지 않는다.

컬럼명만으로는 판단할 수 없다. 2023년판은 같은 컬럼이 `운행시간` 이고, 어느 쪽도
정차 포함 여부를 명시하지 않는다. 그래서 **다른 공표 데이터와 교차검증**했다.

### 2.1 교차검증 근거

`서울교통공사_열차운행현황_20240331.csv` 에 호선별 영업거리·소요시간·표정속도가 있다.
표정속도(commercial speed)는 **정의상 정차시간을 포함한 속도**다.

먼저 공표값끼리의 정합성을 확인했다.

| 호선 | 영업거리 ÷ 공표 소요시간 | 공표 표정속도 |
|---|---|---|
| 1 | 7.8km ÷ 18분 = 26.0 km/h | 26 |
| 3 | 38.2km ÷ 67.5분 = 33.96 km/h | 34 |
| 2 본선 | 48.8km ÷ 90분 = 32.53 km/h | 32.5 |

일치한다. 즉 공표 `소요시간(분)` 은 **정차 포함 실소요시간**이다.

이제 역간 CSV 의 구간별 합계와 비교한다.

| 호선 | 역간 CSV 합계 | 공표 소요시간 | 차이 | 중간역당 |
|---|---|---|---|---|
| 1 | 14.0분 | 18.0분 | 4.0분 | **30.0초** |
| 3 | 51.5분 | 67.5분 | 16.0분 | **30.0초** |
| 6 | 55.5분 | 75.0분 | 19.5분 | 30.8초 |
| 7 | 69.0분 | 87.0분 | 18.0분 | 27.0초 |
| 2 본선 | 65.0분 | 90.0분 | 25.0분 | 34.9~35.7초 |

1호선과 3호선이 정확히 30.0초다. 2호선 본선을 역간 합계로만 계산하면
48.8km ÷ 65분 = **45.05 km/h** 로, 표정속도(32.5)가 아니라 주행속도 영역이다.

**검증에서 제외한 호선과 이유**

| 호선 | 제외 사유 |
|---|---|
| 4 | 공표 구간이 진접~남태령(29역)이나 CSV 는 서울교통공사 관할(26역). 진접선 미포함 |
| 5 | 본선/마천지선 분기라 단일 경로 합계와 공표 소요시간의 정의가 다름 |
| 8 | 역 수 불일치(CSV 19 vs 공표 18). 암사역사공원 반영 시점 차이로 추정 |

### 2.2 중복 보정을 하지 않았다는 확인

역간 CSV 의 값은 정차시간을 포함하지 않는다는 것이 위 교차검증의 결론이다.
따라서 정차시간을 더하는 것은 중복 보정이 아니다.
`06_build_route_graph.py` 와 `09_route_scoring_prototype.py` 어디에도
정차시간을 더하는 기존 로직이 없다는 것도 함께 확인했다.

## 3. 적용

### 3.1 상수

```python
DEFAULT_DWELL_TIME_MIN = 0.5   # scripts/09_route_scoring_prototype.py
```

이 값은 임의 초기값이 아니라 §2.1 의 교차검증에서 유도한 MVP 보정값이다.
**이 점에서 κ=0.5, C0=80, 임계 15분/15%p/5분 같은 설계 파라미터와 성격이 다르다.**
후자는 문서에 "근거 있는 상수가 아니라 초기값"으로 명시돼 있으나,
`DEFAULT_DWELL_TIME_MIN` 은 공표 데이터와의 차이에서 나온 값이다.
다만 노선·시간대·역별 실제 정차시간은 다르므로 단일 상수라는 점은 한계다(§6).

### 3.2 중간 정차역 수 계산

`evaluate()` 안에서 **연속한 ride 엣지 묶음(continuous ride segment)** 단위로 센다.
엣지 종류(`kind`)가 `ride` 가 아니면 segment 를 끊는다.

```
segment 의 ride 엣지 수 k  →  해당 segment 의 중간 정차역 수 = max(k - 1, 0)
dwell_stop_count = Σ max(k - 1, 0)
dwell_time_min   = dwell_stop_count × DEFAULT_DWELL_TIME_MIN
```

이 정의만으로 요구된 규칙이 자동으로 지켜진다.

| 위치 | 처리 |
|---|---|
| 출발역 | 제외 (첫 엣지의 시작점) |
| 목적지 도착역 | 제외 (마지막 엣지의 끝점) |
| 환승 하차역 | 제외 (앞 segment 의 끝점) |
| 환승 승차역 | 제외 (뒤 segment 의 시작점) |
| 같은 열차로 지나가는 중간역 | **포함** |

`evaluate()` 에 들어오는 경로는 가상 노드(`V_ORIGIN_*` / `V_DEST_*`)가 이미 제거된
상태다. `origin_access` / `destination_exit` 엣지는 계산에 관여하지 않는다.

### 3.3 엣지가 아니라 경로 단위로 계산한 이유

같은 엣지라도 경로에 따라 중간역일 수도, 환승역이나 종점일 수도 있다.
엣지 가중치에 미리 섞으면 정확한 판별이 불가능하고, Yen's K-shortest 의
후보 집합 자체가 달라진다. 그래서 탐색 가중치는 건드리지 않고
`evaluate()` 의 경로 집계 단계에서만 더한다.

### 3.4 시간 계산식

```
actual_time_min    = running_time_min      (Σ 승차 엣지 주행시간)
                   + dwell_time_min        (중간 정차)
                   + transfer_walk_min     (환승 도보)
                   + transfer_wait_min     (환승 후 평균 대기)

perceived_time_min = Σ running × (1 + κ · max(congestion − C0, 0) / 100)
                   + dwell_time_min        ← 보정 없이 1회
                   + Σ transfer_penalty_min
                   + transfer_wait_min
```

정차시간은 혼잡도와 무관하게 발생하는 물리적 시간이므로 **혼잡도 배수를 곱하지 않는다.**
`actual` 과 `perceived` 에 각각 정확히 1회씩만 더한다.

환승 대기시간 원칙은 그대로 유지했다. 최초 승차 전 대기시간은 여전히 제외하며,
환승 후 다음 노선의 평균 배차 기반 기대 대기시간만 반영한다.

### 3.5 검산

2호선 신촌 → 잠실 (무환승, 20역 19엣지)

```
원본 역간 주행시간 합계         25.5분
중간역 18개 × 0.5분            + 9.0분
                               ──────
                                34.5분
```

`09_route_scoring_prototype.py` 실행 결과의 `최속_시간` 이 34.5분으로 일치한다.
같은 경로의 `최속_체감` 은 34.9분으로, 34.5분과의 차이 0.4분은 주행시간에만 붙은
혼잡 보정이다. 정차시간 9.0분에는 κ 가 곱해지지 않았음이 값으로 확인된다.

## 6. 재평가 결과 정정 — 계산 통합 전 검증의 한계

### 6.1 처음에 내린 판단

정차시간을 반영한 직후 `10_evaluate_routes.py` 를 세 시나리오로 재실행했을 때,
08:30 3/13 · 18:00 0/13 으로 v1 확인값과 **완전히 같았다.**
이를 "정차시간 보정 후에도 핵심 결론 유지" 로 기록했다.

**이 판단은 검증이 성립하지 않는 상태에서 내려진 것이었다.**

### 6.2 왜 값이 변하지 않았나

`10_evaluate_routes.py` 는 `RouteScorer.evaluate()` 를 쓰지 않고,
`evaluate_path()` 에서 `edge_meta` 기반으로 **비용을 따로 계산**하고 있었다.

정차시간은 `RouteScorer.evaluate()` 에만 들어갔다. 즉 앱에는 반영됐지만
평가 리포트에는 도달하지 못했다. 이후 추가한 강동 직결 분기 통과 규칙도 마찬가지였다.

수치가 그대로였던 것은 결론이 견고해서가 아니라,
**변경이 검증 경로에 도달하지 못했기 때문**이다.

### 6.3 불일치가 드러난 지점

강동 직결 분기를 수정하면서 같은 경로를 두 곳이 다르게 보고하는 것이 확인됐다.

```
방화 -> 마천 (weekday 18:00)
  앱   : 환승 0회 / 88.70분 / 정차 22.0분
  마트 : 환승 1회 / 69.25분
```

19.45분 차이는 정차시간과 환승 시간의 합이다.

### 6.4 통합

`evaluate_path()` 가 `rs.evaluate()` 결과를 받아 10 스크립트 전용 필드만
덧붙이도록 바꿨다. 비용 계산이 한 곳에만 존재하게 된다.
환승역 목록도 같은 통과 규칙을 쓰고, 환승 횟수와 개수가 어긋나면 assert 로 멈춘다.

### 6.5 통합 후 실제 결과

| 시나리오 | 대안 있음 | 통합 전(무효) | 평균 파레토 |
|---|---|---|---|
| weekday 08:30 | **3/13** | 3/13 | 2.08 |
| weekday 18:00 | **2/13** | 0/13 | 2.15 |
| 2025-09-27 18:00 (불꽃축제) | **2/13** (calm) · 3/13 (그 외 모드) | 2/13 | 2.46 |

08:30 은 개수가 같지만 **구성이 바뀌었다.** 응암→고속터미널이 빠지고
방화→마천이 들어왔다(혼잡 감소 58.6%p). "유지" 라고 쓸 수 없다.

18:00 은 0/13 에서 2/13 으로 바뀌었다(안암→삼성 18.5, 방화→마천 42.1).
정차시간이 반영되자 정차역이 많은 우회 경로의 불리함이 드러나면서
파레토 최적해의 구성이 달라졌고, 채택 판정도 함께 움직였다.

이에 따라 `evaluation_strategy.md` D-4 의 핵심 발견과 README 의 수치를 갱신했다.
"저녁에는 시간을 바꿔야 한다"(0/13 근거)와 "평시 0/13 → 불꽃축제 2/13 회복"은
근거를 잃었으므로 삭제했다.

### 6.6 교훈

**같은 계산이 두 곳에 있으면 한쪽만 고쳐도 검증이 통과한 것처럼 보인다.**

수치가 변하지 않았을 때 "결론이 견고하다" 로 해석하기 전에,
**변경된 계산이 실제로 검증 경로에 반영되었는지** 부터 확인해야 한다.
이번에는 "변할 수 있었는데 변하지 않았다" 가 아니라
"변할 수 없는 구조였다" 가 사실이었다.

## 7. 한계

1. **단일 상수** — 실제 정차시간은 노선·역·시간대별로 다르다. 혼잡한 환승역의
   출퇴근 시간대 정차는 30초보다 길다. 현재는 전 구간 동일값이다.
2. **급행·완행 미구분** — 프로젝트 범위인 1~8호선에는 해당 없으나, 향후 확장 시
   통과역이 있는 열차는 이 계산이 성립하지 않는다.
3. **소요시간 차이의 다른 원인은 남아 있다** — 정차시간 반영은 원인 하나를
   제거한 것이지 외부 서비스와의 일치를 의미하지 않는다. 다음이 여전히 미반영이다.
   - 최초 승차 전 대기시간 (설계상 의도적 제외)
   - 역 출입구 ↔ 승강장 이동시간
   - 외부 서비스의 보수적 여유시간 보정
4. **출발 시각의 time_bin 고정** — v1 의 기존 한계. 정차시간을 더해 총 소요시간이
   늘어난 만큼, 시간 전진 미반영의 영향도 그만큼 커진다.
5. **환승 대기는 30분 bin 평균** — v1 의 기존 한계. 정밀 시각표 기반 next departure 는
   이번 범위 밖이다.

### 8.2 로컬 실행 환경 정리

Python 3.12 기반 `metrocalm` 환경을 새로 만들어 해결했다.
배포 대상 Python 버전(3.12)과 로컬을 일치시키는 효과도 있다.
